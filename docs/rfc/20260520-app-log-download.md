# RFC: App Log Download (historic, combined-across-services)

**Date:** 2026-05-20
**Status:** Reviewed (4 iterations) + minimized — ready for implementation. Option D: dedicated singleton app-logs volume.

## Scope block

**Problem:** App developers can view recent per-service container logs live, but cannot download an app's logs over a time window combined across all its services — and today's logs do not survive container recreation (update/restart), so history across critical lifecycle events is lost.

**In scope:**
1. Make per-service app container logs **persist across container recreation and across a failed-update rollback** (the prerequisite without which a historic download is impossible).
2. A new endpoint to **download** an app's logs over a from/to window, **combined and time-interleaved across all of the app's services**, packaged as a downloadable attachment.
3. A **download affordance in the app's Logs tab** (date-range picker, mirroring the existing diagnostic-log download widget) that triggers the combined-across-services download.

**Out of scope (deferred):**
- Switching app containers to the `journald` log driver / journal namespaces (rejected — see Alternatives).
- Changing the existing live viewer / WebSocket stream behavior (they stay tail-N on the current container).
- Backfilling logs for apps installed before this change (forward-looking only; see Migration).
- Reaping orphaned per-service log files left by a service rename (deferred — see Acknowledged D-3).
- Log search, in-UI historic browsing, retention-configuration UI, app-log redaction.

## Decision summary

Keep the existing **k8s-file** log driver (deliberately chosen at `podman.go:516` so rootless per-app users can read their own logs via `podman logs`), but redirect each service's log file onto a **dedicated singleton "app-logs" volume — a thin LV on the data pool** (see Decision 5), mounted once at `/piccolo-core/mounts/app-logs`, holding per-app/per-service subdirs with a bounded `max-size` ring. The download endpoint **copies each service file to a temp snapshot, then performs a streaming k-way merge** over those snapshots (see Decisions 6–7), parses the k8s-file format, filters by absolute time, tags by service, and emits a single interleaved text file.

Validated empirically on a dev host with podman: custom-path log file **survives `podman rm`**, podman **appends** on recreate, and `max-size` rotation keeps the most-recent ~max-size with **no `.1` backup**. **Caveat:** this was the *dev host*, not the real rootless per-app-user setup with `--log-opt path` on the encrypted volume; the load-bearing behaviors (file ownership on first create, rotation while running, read-under-rotation, `podman logs` against a custom path) are listed as device-verification gates below and must pass before ship.

### Why not journald (Alternatives considered)

journald looked simpler (free time-merge, journald-managed retention), but `podman.go:516` documents that **rootless per-app users cannot read the journal back** (`podman logs` fails — not in `systemd-journal`/`adm`, no user journald session). Adopting journald would force re-platforming the existing viewer + stream read paths onto `journalctl`-as-root, reverse a deliberate design choice, and put high-volume app output into the shared system-journal disk budget (risking eviction of piccolod's own diagnostics) while bleeding app logs into the system diagnostic bundle. Per-app journal **namespaces** would isolate that, but podman's journald driver cannot target a namespace without moving app launch onto systemd units — a much larger shift. Rejected for this scope.

## Design decisions requiring sign-off

1. **Retention bound (`max-size` per service).** Proposed `app-log-max-size = 10MB` **per service** (per-service, not per-app). Tunable constant; no UI. (Footprint math in Decision 1a.)
1a. **`app-logs` volume size cap.** The singleton LV is sized to comfortably hold the worst-case footprint plus the transient temp-snapshot doubling during a download — proposed **2 GiB** thin-provisioned (`appLogsVolumeSize` constant alongside `controlPlaneSize`). Thin-provisioned, so it draws physical pool extents only as used. If the LV fills (pathological app count), per-service ring writes fail in isolation — no spillover to `/piccolo-core` or recovery state.
2. **Output format.** Single interleaved `text/plain` file, each line `TS [service] message`, merge-ordered by timestamp across services. (Confirmed: interleaved over zip-per-service.)
3. **Auth level.** Session-gated under the `authed` apps group (not admin-only), matching the existing app-log endpoints. **Note (reviewer C2):** combined with Decision "no redaction," a misbehaving app that echoes an injected secret (e.g. an OIDC client secret) to stdout would appear in the download — but this is **identical to the existing live viewer's exposure** (same bytes, same auth class), so it is not a new exposure — though a downloaded file is durable/forwardable off-device (larger blast radius than the ephemeral viewer, same bytes/auth class). No redaction; flagged for product sign-off.
4. **Time-window semantics.** Reuse `parseDiagnosticRange` (`gin_diagnostic.go`) for `?from=&to=` (YYYY-MM-DD, ≤7-day window). Bounds and log timestamps are both compared as **absolute `time.Time`** (k8s-file timestamps carry their TZ offset), so the window is TZ-correct regardless of host timezone — see Decision 7.
5. **Logs live on a dedicated singleton `app-logs` volume (`VolumeClassAppLogs`) — a v3 `service-data` thin LV on the data pool** (same backing as application volumes), sized per Decision 1a. (Why not the data volume / control-plane loop / a pool directory / per-app volumes: see Alternatives — block-native has no writable pool filesystem, durable app storage is an LV; the control-plane loop lives on the boot-critical `/piccolo-core`.) **LV-name collision guard:** its LV name must lie **outside** the `vol-app-{instanceID}` namespace that `RollbackDataVolume`/`ensureAppVolume` operate on (e.g. `vol-logstore`, since an app named `logs` derives `vol-app-logs`); the volume ID is also added to `ReservedNames` as defense-in-depth. As a v3 volume it participates in keyslot reconciliation like any other (acceptable/desirable — it's an encrypted device with its own key). **Lifecycle: the mount is bound to the unlock session, disjoint from container lifecycle — like the control-plane volume, NOT like a per-app data volume.** It mounts once on unlock and stays mounted for the whole unlocked session; app containers starting/stopping/recreating underneath it never attach or detach it. (This is why logs survive container recreation at the storage layer: the file's home is stable while writers are replaced.) The only teardown is crypto-lock, which deactivates the whole pool. Mounted at its `paths.MountDir(...)` mountpoint under `/piccolo-core/mounts/...` (the mountpoint is a bare dir on core; the *data bytes live on the pool LV*). Layout: `{appLogsMount}/{instanceID}/{svcName}.log`. Invariants:
   - *(a) Not reverted by data-volume rollback* — `RollbackDataVolume` (`luks_volume_manager.go:1992`) renames only `vol-app-{instanceID}`; the singleton `app-logs` LV is never its target. A failed update triggers rollback, which is exactly when the dev needs the crash logs — surviving rollback is the headline requirement.
   - *(b) Encrypted at rest with its own key* — a thin LV gets per-volume LUKS2 (same as application volumes), so this is **stronger** than the iter-3 partition-key idea; no per-app-key isolation between apps within the shared volume (A-3), acceptable on a single-user appliance.
   - *(c) Own size budget, off the boot-critical partition* — the LV draws from the data pool's GBs, not `/piccolo-core`; app logs cannot ENOSPC-starve recovery keyslots (control-plane) **nor** PCV/app-state writes (the `/piccolo-core` blast radius from iter-3 B1). If the `app-logs` LV fills, writes fail in isolation on that ring.

   Consequences: failed-update logs survive rollback (✓); a clone derives a new instanceID → its own empty subtree (✓); the **volume is never destroyed per-app** — only per-app subdirs are created/removed (Site 5), and the volume lives for the device's lifetime (destroyed only on factory reset).
   - **Acknowledged cost:** this is a genuine scope increase — a new `VolumeClassAppLogs` + provisioning + mount lifecycle (Sites 0a/0b). The user accepted this trade in choosing Option D over keeping logs on the data volume.
6. **(NEW — resolves red-team B2/Finding-3, reviewer S1) Read-under-rotation contract + temp location.** The download **snapshots each service file (copy to a temp path) before merging**, then merges the stable copies, then deletes them — rather than holding long-lived readers on files conmon may be rotating/appending. This prevents a rotation mid-merge from feeding a truncated/rewritten inode into the reader (garbage/short read). **Temp copies are written under the `app-logs` mount** (same pool-backed LV, off `/piccolo-core` and off the control-plane); cleanup is via `defer` that survives handler panic and client-disconnect/context-cancellation, and the startup reaper (Site 5) also sweeps stale temp artifacts (covers SIGKILL leaks). A torn trailing line (writer mid-append at snapshot time) that fails `parseK8sFileLogLine` is **dropped, not errored** (consistent with the empty-file rule). The live viewer/stream remain out of scope but their behavior under `max-size` rotation is added to the verification gates.
7. **(NEW — resolves red-team B3, S4) Merge under non-monotonic input.** Files are appended in write order; timestamps are normally monotonic but a wall-clock step (NTP correction, RTC-less RPi cold boot before sync) can introduce a backward jump within a file. The merge therefore: (a) compares **parsed absolute `time.Time`**, explicitly **rejecting the lexical-string-compare optimization** (unsafe across TZ/clock changes); (b) **does not early-terminate any reader** on timestamp — every line is read and every line is window-filtered independently, so a backward step cannot silently truncate a service's contribution; (c) treats cross-service ordering as **best-effort** — a heap over current heads yields correct order except across an intra-file backward step, where local misordering is accepted and documented. The unqualified "monotonic" claim from iteration 1 is withdrawn.

## Q2 — named behavior at each site (default-by-omission audit)

- **Site 2, `LogPath`/`LogMaxSize` empty:** identical to today (graphroot default). Only service containers set them; anchor, diagnostic ephemeral runtime, and any other `buildCreateArgs` caller unaffected.
- **Site 6, missing/empty subtree or file** (app not yet recreated post-upgrade, service never logged): zero lines, **not** an error — download still succeeds, possibly empty/partial.
- **Site 6, `app-logs` volume unavailable** (crypto locked / not yet attached, via `AttachStateOf`): distinct **transient error** (retryable), explicitly *not* conflated with the empty case above (resolves reviewer S-2).
- **Site 6, requested `from` precedes the oldest retained line** (ring evicted it): emit a per-service header line stating the oldest available timestamp, so an empty/short result is distinguishable from "data evicted."
- **Site 6, line cap exceeded:** emit a truncation marker line; cap mirrors `diagnosticMaxLines` intent.
- **Site 7, torn trailing line** (writer mid-append at snapshot): line fails parse → dropped, not errored.
- **Site 7, oversized single logical line:** truncated at the cap with a marker (memory-bound guarantee).
- **Site 7, non-UTF8 / binary stdout:** passed through verbatim into the `text/plain` body (dev's own output; acknowledged, not transformed).
- **Site 9, app-log redaction:** **none** (see Decision 3 — parity with the existing live viewer; not a new exposure).

## Q3 — invariants preserved (composition-blindness audit)

*Covered by their owning decisions (cross-refs, not re-derived):* rollback safety → Decision 5(a)/(c); encryption → 5(b); clone correctness → Decision 5; per-app subdir teardown + fail-closed reaper → Site 5; read-under-rotation → Decision 6; clock-step + TZ → Decisions 4/7. The bullets below audit distinct composition sites:

- **Lifecycle parity with the data volume (verified — the B-NEW-1/B-NEW-2 resolution):** the `app-logs` LV rides the *same* pool lock/unlock coordination the per-app data volume already uses. On unlock, volumes attach before any container is created/started (`RestoreServices`→`ensureAppVolumeLayout`→`ReconcileOnce`, `app_manager.go:616-619`), and the singleton attaches before the unlock event is published (Site 0b) — so a container is never created against an unmounted log volume. On lock, the pool deactivates under still-running containers exactly as for data today; conmon holds an **open fd** (it does not re-resolve the path per write), so a deactivated volume yields **EIO on that fd, not a fall-through to the bare `/piccolo-core` mountpoint** (that would require a *new* container opening the path mid-lock, which can't happen). Not a new hazard beyond what data volumes already incur. ✓
- **Mount-inactive fail-safe (backstop to Site 0b fail-open):** if the mount is inactive at create time, Site 3 omits `LogPath` (default driver) — app still starts, a later reconcile re-fixes it, logs never land on the bare mountpoint. ✓
- **Cross-app isolation (A-2):** `{appLogsMount}` parent `0700 root:root`; per-app subdirs chowned per credential; instanceIDs/svcNames are piccolod/manifest-controlled → no traversal. ✓
- **First-create file ownership:** conmon (per-app user) writes; piccolod (root) reads. Whether conmon's first file-create yields root-readable perms under the per-app UID is **unverified** → device gate (fallback: read as the per-app credential). 
- **`ValidateContainerSpec` / `ValidatePath`:** `ValidatePath` rejects `:`; the log path has none. Confirm the new spec fields pass — impl check.
- **Log-path parent must pre-exist:** podman won't create it; Site 3/5 create the dir first. ✓
- **RPi-4 cost:** streaming k-way merge, `O(k)` line-capped memory over `k`≈2–5 ring-bounded readers + one bounded snapshot pass; single-flight bounds concurrency — acceptable on RPi-4.

## Sequencing

1. **Volume foundation** (Sites 0a/0b): `VolumeClassAppLogs` + `ensureAppLogsVolume` (thin LV on pool) + mount wiring in the post-unlock sequence, ordered before app-container reconcile. Verify the volume provisions, attaches when unlocked, and reports unavailable when locked.
2. **Persistence wiring** (Sites 1–5): spec fields + `buildCreateArgs` emission + per-app subdir provisioning/teardown/reaper + per-service log-path wiring with the mount-inactive fail-safe. After this, recreated containers accumulate persistent, rollback-surviving, bounded logs. Verify viewer/stream + ownership + rotation on device.
3. **Read + parse** (Sites 6–7): `WriteHistoricLogsForApp` + capped parser + snapshot/merge.
4. **Endpoint** (Sites 8–9): route + handler + single-flight + `parseDiagnosticRange`.

## Migration

**Forward-only (this release).** The custom `LogPath` is baked at container *create* time, so it applies only to containers created after the upgrade. A piccolod upgrade re-locks crypto and the apps are restarted on unlock — but reconcile **restarts** the persisted containers (graphroot is on the per-app data volume), it does **not** recreate them, so existing apps keep logging to the old graphroot path until their **next recreate (app update / reinstall)**. Pre-upgrade logs are not migrated or downloadable (no backfill).

To avoid a confusing empty download for not-yet-migrated apps, `WriteHistoricLogsForApp` emits a header line when the subtree is absent — *"No persistent logs for this app yet — restart or update the app to start collecting them"* — which the UI surfaces as a notice.

**Migrate-on-upgrade is deferred to a fast-follow** (see deferred memory `deferred_app_log_migration`). Three options were weighed — (a) hint only [shipped], (b) version-gated one-time recreate-all on first post-upgrade unlock, (b′) reconcile recreate-on-`LogPath`-drift. Apps are down on every upgrade anyway, so (b)/(b′) add no new outage; the residual cost is mass-recreate blast radius (b) or widening reconcile's recreate-on-drift triggers (b′, same class as the deferred catalog-manifest-sync issue). Deferred so the reconcile-path change gets its own design + hardware validation rather than riding this release.

## Device-verification gates

- `podman logs` against a **running** container with custom `--log-opt path` (viewer/stream regression).
- **Rotation while running:** a chatty service crossing `max-size` mid-run — confirm (a) `podman logs` viewer still returns sane output, (b) a concurrent download (reading temp snapshots) is unaffected.
- **First-create file ownership:** conmon (per-app user) creates the log file root-readable under the per-app UID in the real per-app-user setup.
- **Rollback:** trigger a failed update → rollback; confirm the failed generation's logs remain downloadable (Decision 5).
- **Clock step:** simulate an NTP backward step; confirm the merge does not truncate a service's contribution.
- **Volume mount lifecycle:** `app-logs` provisions on first unlock, attaches on every unlock, reports unavailable when locked; mount is active before apps start (else Site 3 fail-safe engages and logs land on the default driver, never the bare `/piccolo-core` mountpoint).
- **Locked-boot reaper:** reboot, leave crypto locked, confirm the reaper does **not** delete any subdir (fail-closed, B2).

## Acknowledged / deferred

- **D-1 (red-team A1):** concurrent-download contention — mitigated by single-flight per app (Site 9); cross-app concurrency accepted (operator-initiated, not remote-adversarial).
- **D-2 (reviewer C1):** no explicit marker at a container-recreation boundary in the interleaved output — timestamps make the gap visible; seamless append is the intended UX.
- **D-3 (red-team S1):** orphaned `{oldName}.log` after a service rename is still *read* (Site 6 enumerates all `*.log`), but not *reaped* — it counts against footprint until uninstall. Reaping on rename deferred (out of scope).
- **UX-1 (download is combined, viewer is per-service):** the Logs tab's live viewer filters to one service via a dropdown; the download deliberately ignores that selector and always emits all services interleaved (deliverable #2). Rationale: the download's value is cross-service correlation; a per-service download would duplicate what the viewer already shows. A per-service download variant is a possible future addition, not v1.
- **A-3 (per-app-key isolation between apps forgone):** the `app-logs` LV has its own per-volume LUKS2 key (encrypted at rest ✓), but all apps' logs share that one key — no per-app cryptographic isolation *between* apps within the shared volume. Accepted for a single-user appliance; per-app log encryption out of scope.
