# RFC: LAN HTTPS with Self-Signed Certificates

## Problem Statement

The Piccolo portal served at `http://piccolo.local` cannot use the browser Clipboard API because it requires a [secure context](https://developer.mozilla.org/en-US/docs/Web/API/Clipboard_API#security_considerations) (HTTPS or localhost). This breaks:

1. **Terminal copy/paste**: Users cannot copy terminal output via Ctrl+C or right-click → Copy.
2. **Log viewer copy**: Selected log text cannot be copied to clipboard.
3. **Any future clipboard-dependent features**: File upload via paste, etc.

The `execCommand('copy')` fallback works inconsistently across browsers and is deprecated. HTTPS is the proper solution.

## Existing Infrastructure

Piccolo already has the building blocks:

1. **Internal CA** (`internal/crypto/internal_ca.go`): ECDSA P-256, 10-year self-signed CA, issues 1-year server certificates.
2. **Internal HTTPS listener** (`internal/server/gin_server.go`): Runs on `0.0.0.0:443`, serves the same Gin router, currently used for OIDC back-channel communication between containers and the portal.
3. **Server certificate**: Generated at unlock time with SANs for `piccolo.local` and `localhost` only.

The HTTPS listener already works for LAN access — users can visit `https://piccolo.local` today. However:
- The certificate only covers `piccolo.local` and `localhost`, not `piccolo-{machineId}.local` or app alias domains.
- Certificates are loaded once at startup and cannot be refreshed when new hostnames are added (app installs).
- There is no UI guidance for users to discover HTTPS or trust the CA.

## Proposed Solution

### 1. Dynamic Server Certificate SANs

Extend `InternalCA` to generate server certificates covering all mDNS-advertised hostnames.

**New method:** `EnsureServerCertificateForHosts(hostnames []string) (bool, error)`

- Accepts a dynamic list of DNS names
- Compares requested SANs against existing certificate
- Regenerates only if SANs differ or cert expires within 30 days
- Returns `true` if a new certificate was written to disk

The existing `EnsureServerCertificate()` remains unchanged for backward compatibility.

**Hostname format** (from `NameRegistry` at `names.go:166-178`):

| Hostname | Description |
|----------|-------------|
| `piccolo.local` | Gateway domain (if leader) |
| `piccolo-{machineId}.local` | Device-specific domain |
| `{app}-piccolo.local` | App alias (hyphenated 2-level, NOT dot-separated) |
| `localhost` | Loopback (DNS SAN) |
| `127.0.0.1` | Loopback (IP SAN) |

### 2. Hot-Reload TLS via GetCertificate

Replace `ListenAndServeTLS(certPath, keyPath)` with `tls.Config.GetCertificate` callback.

**Current behavior** (line 1730):
```go
s.internalSrv.ListenAndServeTLS(certPath, keyPath)
// Reads cert once at startup — new connections use stale cert
```

**Proposed behavior:**
```go
tlsCfg := &tls.Config{
    GetCertificate: func(*tls.ClientHelloInfo) (*tls.Certificate, error) {
        return s.loadServerCert()
    },
    MinVersion: tls.VersionTLS12,
}
s.internalSrv = &http.Server{
    Addr:      "0.0.0.0:443",
    Handler:   s.router,
    TLSConfig: tlsCfg,
}
s.internalSrv.ListenAndServeTLS("", "")
// Each new connection loads cert from disk — picks up refreshed SANs
```

This avoids stopping/restarting the listener (which would drop in-flight OIDC connections).

### 3. Event-Driven Certificate Refresh

When app aliases change (install/uninstall), the mDNS `NameRegistry` updates its hostname list. The server subscribes to `TopicServiceEndpointsChanged` and refreshes the certificate:

```
App installed → TopicServiceEndpointsChanged → NameRegistry updates
    → refreshServerCertSANs() → EnsureServerCertificateForHosts()
    → New cert written to disk → Next TLS handshake uses new cert
```

**Lifecycle management** (follows existing `ObserveServiceEndpoints` pattern in `mdns/manager.go:443`):
- Previous subscription canceled before creating new one (handles re-lock/unlock cycles)
- Unsubscribe function stored on `GinServer` struct, called in `Stop()`

### 4. CA Certificate Download

**Backend:** `GET /api/v1/system/ca.crt` — unauthenticated endpoint serving the CA certificate PEM. Required before login (user needs to trust CA to access HTTPS portal).

**UI:** "LAN Security" card in Settings → System tab:
- Shows HTTPS availability info
- "Download CA Certificate" button using existing `downloadTextFile()` utility
- Brief instructions for trusting the CA in the browser

**Note:** Accepting the browser's self-signed certificate warning already provides a secure context (Clipboard API works). The CA download eliminates repeated warnings — it's a UX improvement, not a hard requirement.

### 5. Terminal Keyboard Shortcuts (Ctrl+Shift+C/V)

Independent of HTTPS, add Linux terminal convention shortcuts:

| Shortcut | Terminal Widget | Log Viewer |
|----------|----------------|------------|
| Ctrl+Shift+C | Copy selection | Copy selection |
| Ctrl+Shift+V | Paste from clipboard | N/A (read-only) |
| Ctrl+C | Copy if selection, else SIGINT | Copy if selection |
| Cmd+C (macOS) | Copy if selection, else SIGINT | Copy if selection |
| Cmd+V (macOS) | Paste | N/A |

These work on both HTTP (via `execCommand` fallback) and HTTPS (via Clipboard API).

### Certificate Lifecycle

```
Device boot
    │
    ▼
Crypto unlock → ensureInternalCA() → EnsureServerCertificate()
    │                                 (piccolo.local, localhost)
    ▼
startInternalHTTPSListener()  ── GetCertificate callback ──► loads from disk
    │
    ▼
refreshServerCertSANs()  ──► EnsureServerCertificateForHosts()
    │                         (all mDNS hostnames + localhost)
    │                         Regenerates cert if SANs differ
    ▼
Subscribe TopicServiceEndpointsChanged
    │
    ▼
App install/uninstall → event → refreshServerCertSANs()
                                  → cert updated on disk
                                  → next TLS handshake uses new cert
```

## Design Decisions

1. **Gateway leadership and SANs**: The certificate always includes `piccolo.local` regardless of gateway leadership state. Leadership determines which device *responds* to `piccolo.local` via mDNS, not which device's cert covers it. Including it unconditionally avoids cert regeneration churn on leadership changes and ensures the cert works if leadership is gained later.

2. **No IP SANs for LAN addresses**: LAN IPs can change (DHCP). Including them would require regenerating the cert on IP changes. `127.0.0.1` is included since it's static. Users accessing via LAN IP will see a cert mismatch warning — this is acceptable since hostname access is the primary path.

3. **No certificate fingerprint endpoint**: The CA cert is downloaded over HTTP on the same LAN. An attacker who can MITM the HTTP download can also MITM the fingerprint endpoint. Physical LAN trust is the security model here.

## Security Considerations

1. **Self-signed CA scope**: The CA is device-local. Trusting it only affects this device's certificates.
2. **CA cert download over HTTP**: The CA cert is public key material — safe to serve over HTTP. It's no different from downloading a root CA from a website.
3. **No HTTP-to-HTTPS redirect for .local**: Users choose their protocol. The existing `httpsRedirectMiddleware` already skips `.local` domains (line 1765).
4. **Certificate key protection**: Server private key stored at `{bootstrap_dir}/certs/server.key` with `0o600` permissions on encrypted bootstrap volume.
5. **TLS version**: Minimum TLS 1.2 enforced via `tls.Config.MinVersion`.
